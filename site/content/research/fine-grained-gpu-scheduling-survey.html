01先直接回答你的问题

有，而且这是一条相当成熟的研究脉络——但「保证算力」和「细粒度调度」是两件常被混为一谈的事，前者远比后者稀缺。调研结论可以压缩成三句话：

结论一
机制早已存在
SM 级切分的硬件/运行时原语齐全：MIG（硬）、MPS 线程百分比、CUDA Green Context（12.4+，SM 数粒度）、libsmctrl（TPC 掩码）。底层不缺手段。
结论二
绝大多数是
「隔离」不是「保证」
REEF / Orion / Paella / TGS / Tally 等主流系统本质都是优先级 + 干扰最小化，只承诺高优先级任务不被拖慢，不对任何一方承诺算力下限。
结论三
LLM 侧断层明显
单卡内已有人按 SM 分（POD-Attention、Bullet、MuxServe）；但一旦跨到多租户/多请求，全部退化成「显存字节 / token 计数 / 整卡数」。这就是空白区。
一句话概括你要找的东西：真正意义上「保证 X 算力」的工作，目前只存在于实时系统社区（ECRTS/RTAS，有可证明的界）和刚刚出现的 LithOS（SOSP'25，TPC quota + work-conserving stealing）。在 LLM serving 领域，还没有任何一篇论文把「给租户 A 保证 30% 算力」当作一等公民的资源单位——这正是第 7 节列出的 gap 所在。

02机制层：能用来切算力的原语

这一层决定了你的系统最强能做到什么保证。关键区分是 HARD（硬件强制，物理隔离）与 SOFT（尽力而为，可被争用穿透）。很多论文把 MPS 的 ACTIVE_THREAD_PERCENTAGE 当作硬配额来用，这是不成立的。

机制隔离强度分区对象粒度关键事实与限制
MIG
A100/H100/H200/B200		HARDSM + L2 + 显存带宽 + 显存 + 拷贝引擎，全维度物理分区预定义 profile，最细 1/7（Blackwell 部分配置 1/8）唯一真正的硬件级强隔离，含 fault isolation。代价：重配置需 GPU reset（要停掉所有持句柄进程）；跨实例不支持 NVLink P2P，NCCL 不支持 MIG —— 所以 MIG 实例基本无法参与分布式推理的集合通信。这条限制对你的方向很关键。
MPS
ACTIVE_THREAD_PERCENTAGE		混合SM 线程并发配额；Volta+ 有独立虚拟地址空间百分比（软配额）NVIDIA 官方措辞是 "provisioning for QoS"，是上限而非保证，client 设置只能比 daemon 更紧。显存地址隔离是硬的，但 fault isolation 仍是已知弱点（NVIDIA 论坛已承认）——MPS server 崩溃会带走所有 client。
CUDA Green Context
CUDA 12.4+ driver API
13.1 起有 runtime API		SOFTSM 数量 + work queue；L2 与显存带宽仍全卡共享SM 粒度；Hopper 上须为 8 的倍数目前最值得关注的原语。官方明确写 "concurrent execution is not guaranteed"，只保证分到的 SM 数量这个静态描述。实测坑：decode kernel 大量读显存会冲刷 L2，反过来拖慢共享芯片的 compute-bound kernel。PyTorch 2.12+ 有 torch.cuda.green_contexts（Beta）；FlashInfer 已有成熟 green_ctx 模块；vLLM/SGLang 尚未作为稳定特性发布。
libsmctrl
RTAS 2023, UNC		SOFTTPC 掩码（篡改 TMD 的 SM_DISABLE_MASK）TPC 级纯用户态、不需 root、不改源码。支持 CC 3.5–8.9；Hopper（CC 9.0）起掩码位与软件可见 TPC ID 不再一一对应，Blackwell 支持情况未验证。论文自陈：贪心 block 分发 + task slot 耗尽仍会让无关分区互相阻塞 —— 不是硬隔离。不兼容 CUDA Graphs / Dynamic Parallelism。
Stream Priority /
Persistent Kernel		无保证调度顺序 / 软件占位无固定粒度Stream priority 只影响 block 派发顺序，不预留 SM；persistent kernel（如 CUTLASS Stream-K）是用户态「占坑」技巧，其它进程的 kernel 仍可能被派到同一 SM。
AMD MI300X
SPX / DPX / CPX		HARDXCD（chiplet）级，配 NPS1/2/4 决定 HBM 分组1 / 2 / 8 分不需 Hypervisor，驱动层生效。但重启或卸载 amdgpu 驱动后自动恢复 SPX，不像 MIG 那样持久。另有 CU masking（软）对应 libsmctrl。
K8s 时间片
nvidia device-plugin		SOFTGPU 时间片副本数官方文档原话：replica 之间没有显存隔离也没有故障隔离。只是均分时间片，最弱的一档。
HAMi / Volcano-vGPU混合用户态 CUDA API 劫持（ld.so.preload）显存 MB / 算力 %显存是真硬限（拦截 cuMemAlloc，超额直接返回 OOM）；算力是令牌桶 + 后台闭环调节的软限速（耗尽则 nanosleep），短时仍会超/欠配。理论上可被绕过（直接调用未 hook 的符号）。
阿里云 cGPU偏 HARD内核态驱动层拦截显存与算力GiB / 百分比下沉到内核驱动而非用户态 hook，比 HAMi 更难绕过，但仍是软件实现而非物理电路切分。
KAI Scheduler
Run:ai，2025 由 NVIDIA 开源		不提供纯编排层（DRF、层级队列、gang scheduling）—本身不做任何隔离，隔离能力完全取决于下游委托的 GPU Operator（时间片 / MIG）。选型时容易误判的一个点。
选型建议（针对你的研究）：如果要做「保证算力」的系统研究，Green Context 是当下最合适的载体——SM 粒度、有官方 API、PyTorch/FlashInfer 已有支持、能进 CUDA Graph。它的 SOFT 属性恰恰是研究机会：把「分到 N 个 SM」变成「保证 N 个 SM 的有效算力」，中间隔着 L2 与显存带宽的争用，这段路没人铺完。

03粒度阶梯：现有系统各站在哪一级

从粗到细排开，可以清楚看到「大家都在往下走，但走到 SM 级之后就分岔了」。越靠下的层级，越少有系统真正触达硬件寄存器。

整卡 / job 级
Gandiva（OSDI'18，job 迁移+时间片打包）· ServerlessLLM（OSDI'24，冷启动优化）· 绝大多数 K8s 调度器
请求 / batch 级
Clockwork（OSDI'20，靠执行时间可预测性做准入控制，接近保证但保证的是「时间」不是「空间」）· Shepherd（NSDI'23）· Nexus（SOSP'19，ILP 打包进 GPU lane）· Usher（OSDI'24，干扰感知打包）
Token 级
Sarathi-Serve（OSDI'24，chunked prefill 的 token 预算）· VTC（OSDI'24，token 公平队列）· Aegaeon（SOSP'25，token 边界抢占式模型切换，单卡容纳 7 个模型）· FlexLLM（NSDI'26，推理与微调 token 交错）· ConServe（token + layer 级抢占）
Kernel / 算子级
REEF（OSDI'22，reset-based 微秒级抢占 + DKP）· Orion（EuroSys'24，感知 SM 需求的算子调度）· Tally（ASPLOS'25，block 级非侵入调度）· Salus（MLSys'20，快速 job 切换）· NanoFlow（OSDI'25，算子按功能单元静态分区）
Thread block / CTA 级
Paella（SOSP'23，编译器插桩上报 block 落位，按 SM 空闲情况延迟提交）· LithOS（SOSP'25，kernel atomization：透明把 kernel 切成可调度 atom）· POD-Attention（ASPLOS'25，CTA 内查 SM ID 原子决定跑 prefill 还是 decode）
SM / TPC 硬件级
LithOS（TPC 分配 + TPC stealing，唯一明确给出 compute quota 语义的通用系统）· Bullet（ASPLOS'26，SM masking 在 prefill/decode 间动态重分）· GSLICE（SoCC'20，MPS SM% 动态配额）· Gpulet（ATC'22，MPS 空间划分 + 干扰模型，SLO 违反 <1%）· MuxServe（ICML'24，MPS SM 粒度多 LLM 共享）· libsmctrl / Fractional GPUs（机制层）
Warp 级 / 可证明
ECRTS'24 Predictable GPU Sharing（实时锁协议 + 动态 resizing，有可证明的容量损失界）· ECRTS'25 WCET bounding（warp → thread block 的数学上界，Rodinia 上过估 8–16%）· UNC 实时组的 GPU 调度逆向工程系列

注：Prism（OSDI'26）站在一个正交维度——显存页级（2MB）的 ballooning，论文明确说「计算共享已被 MIG/vGPU 研究充分，显存弹性共享才是空白」，所以它有意不做算力分配。这个立场本身值得你在 related work 里引用与反驳。

05LLM serving 侧：谁真的在按 SM 分？

这是和你上一轮调研直接接上的部分。答案分成两半，而这两半之间的落差就是最值得做的东西。

已经在做：单卡内、按「算子类型」分

  • POD-Attention（ASPLOS'25，UW + MSR）— 单 kernel 融合 prefill 与 decode attention。每个 CTA 启动后由 leader thread 查硬件计数器拿到自己的 SM ID，用原子操作动态决定跑 prefill 还是 decode。关键是它对硬件如何把 CTA 映射到 SM 完全不敏感——这是运行时绑定，不是静态假设。arXiv:2410.18038
  • Bullet（ASPLOS'26，中山大学）— 最直接命中你问题的一篇。用 SM masking 在 prefill（layer 粒度）与 decode（step 粒度）之间微秒级动态重分配 SM 数量，配一个只需 18–30 次采样的 "SM-scaling roofline model" 预测不同 SM 预算下的延迟，同时满足 TTFT 与 TPOT 的 SLO。arXiv:2504.19516 · 已开源
  • NanoFlow（OSDI'25，UW）— 把 batch 拆成 nano-batch，把 GPU 功能单元（Tensor Core / CUDA Core / 显存带宽 / NVLink）按算子类型分区并流水重叠。注意它是离线搜索出的静态配置，不是运行时动态分配。后续 DynaFlow（MLSys'26）把它泛化为可编程调度框架，开始用 CUDA streams + green contexts 管并发。
  • MuxServe（ICML'24，UCSD）— 基于 MPS 做 SM 粒度的多 LLM 空间复用 + prefill/decode 时间复用，ADBS 算法动态分配，带公平性约束（归一化算力/显存消耗差需在 ε 内）。
  • Green Context 实践—— FlashInfer 的 green_ctx 已能按固定比例（如 P:D = 8:2）把 prefill / decode 分流到不同 SM 分区，公开案例报告 H200 上约 +34% 吞吐、消费级卡近 +60%，并显著收窄 ITL 分布。但尚未进 vLLM/SGLang 主干。

还没人做：跨「租户 / 请求」按算力分

一旦从「prefill vs decode」跨到「租户 A vs 租户 B」，所有系统都退化到三种粒度之一：

  • 显存字节 — Prism（OSDI'26）的 ballooning、S-LoRA 的 unified paging
  • token 计数 — VTC、Aegaeon、FlexLLM
  • 整卡 / 实例数 — ServerlessLLM 及绝大多数集群调度器

为什么 token 公平 ≠ 算力保证

VTC（OSDI'24）值得单独辨析，因为它最容易被误认为已经解决了这个问题：

  1. 它保证的是相对公平（两个 backlogged 客户端服务差异有 2× 紧上界），不是「你固定拿到 30% 算力」的绝对下限。
  2. token 数 ≠ FLOPs。prefill token 与 decode token 的计算密度差一个数量级；同样的 token 计数在不同 batch 组成下对应的 SM 占用完全不同。VTC 从不核算底层 SM/TFLOPs。
  3. 它是 work-conserving 排队（类似网络 fair queueing 的 virtual time），租户空闲时份额会被别人占走 —— 这与「预留给你、不用也不给别人」的 reservation 语义相反。

一句话：VTC 解决的是「队列里怎么排更公平」，不是「怎么把硬件切一块保证给你」。

06核心断裂点：为什么「保证 X TFLOPs」这么难

这不是没人想到，而是有三个真实的技术障碍。把这三条讲清楚，本身就是一篇论文 introduction 的骨架。

障碍一
SM 数 ≠ 有效算力
Green Context 只切 SM 与 work queue，L2 cache 与显存带宽仍是全卡共享。分给你 32 个 SM，隔壁 decode kernel 一冲刷 L2，你的实际算力就掉了。「分配量」到「保证量」之间隔着未被隔离的共享资源。
障碍二
LLM 负载密度
本身不稳定
推理的计算密度随 batch 组成（prefill/decode 比例、序列长度分布）剧烈波动，SM 数量到有效 TFLOPs 的映射不是常数。这正是 POD-Attention / Bullet 只敢在「算子类型」间分 SM、不敢在「租户」间分的根本原因——算子的 compute/memory-bound 特征稳定可建模，跨租户负载不可预测。
障碍三
硬保证的
那一档不能通信
唯一的硬隔离 MIG 不支持跨实例 NVLink P2P，NCCL 也不支持 MIG。这意味着硬保证与分布式推理天然互斥——想要 TP/EP，就只能退回软隔离。这条约束在文献里被讨论得远远不够。

07五个可攻的 Gap

Gap A · 把「分到 N 个 SM」做成「保证 N 个 SM 的有效算力」
障碍一的正面攻击。Green Context 官方明说不保证并发，L2/带宽仍共享；ETH 的 Understanding GPU Resource Interference One Level Deeper（SoCC'25）刚刚把这层争用测清楚，但还没有系统把「补偿这层争用」做进调度器——即：观测到 L2 被冲刷导致有效算力下降后，动态补发 SM 或限制干扰方。这是一个定义清晰、baseline 明确的题目。
怎么做：单卡即可。Green Context 划分 + 用 .cs/evict-first cache hint 与 SM 补偿两条路线对比，指标是「名义 SM 份额 vs 实测有效 FLOPs 达成率」。这条曲线本身就是核心图。
Gap B · LLM serving 的多租户算力配额（最大的空白）
如第 5 节所述：没有任何一篇论文把「保证租户 A 拿到 30% 算力」当作一等公民的资源单位做准入控制与调度。LithOS（SOSP'25）在通用 ML 负载上做到了 TPC quota + work-conserving stealing，但没有针对 LLM 的 prefill/decode 二相性；Bullet 做到了 SM 动态分配，但分配对象是算子类型而非租户。把 LithOS 的 quota 语义搬到 LLM 的两相负载上，是一个现成的缝。
怎么做：2 节点足够。在 vLLM/SGLang 上加一层 Green Context（或 libsmctrl）的租户配额层，用 ServeGen 生成多租户负载，对比 VTC（token 公平）与你的算力配额在「租户被邻居拖慢多少」上的差异。关键实验：制造一个高 prefill 占比的恶意邻居，证明 token 公平失效而算力配额不失效。
Gap C · 硬保证与集合通信的互斥问题
障碍三。MIG 给硬隔离但断掉 NVLink P2P 与 NCCL；软隔离（MPS/Green Context）保住了通信但失去保证。「既要分布式并行、又要算力保证」目前无解，而这恰恰是多租户 LLM 集群的真实需求。文献里几乎没人正面处理这个矛盾。
怎么做：先做 measurement study：量化「Green Context 分区下 NCCL 集合通信的性能与隔离性」——分区是否会让 all-reduce 的 SM 占用越界？多租户同时 all-reduce 时干扰有多大？这个测量目前没有公开数据，做出来就有价值。需要 2+ 节点 RDMA。
Gap D · 算力配额的「可证明性」从实时社区搬过来
ECRTS'24 的 Predictable GPU Sharing 有可证明的容量损失界，ECRTS'25 有 warp→thread block 的 WCET 数学上界（Rodinia 上过估仅 8–16%）。这套分析框架和系统社区几乎是两个平行宇宙——系统论文谈 SLO 达成率（经验），实时论文谈可证明界（理论），没人把两者接起来。给 LLM 推理的 SM 配额一个可证明的下界，是个漂亮的交叉题。
怎么做：理论为主、实验为辅，对资源要求最低。风险是审稿口味——投 RTSS/ECRTS 接受度高于 OSDI。
Gap E · 细粒度算力调度与 PD 分离 / EP 的联合设计
承接你上一轮调研：现在 PD 分离是跨 GPU 的（DistServe / Mooncake），而 POD-Attention / Bullet / Green Context 证明 PD 也可以在单卡内按 SM 分离。那么最优的分离粒度到底在哪一层？跨节点、跨卡、卡内 SM——这三层的选择边界没人系统研究过。同理，MoE 的 EP 与 SM 配额如何联合（专家负载不均 → 该给谁更多 SM）也是空的。
怎么做：这条最能和你已有的调研接上。在单节点 8 卡上，把「跨卡 PD 分离」与「卡内 SM 分离」做成同一套框架下的两个配置项，扫出相图。和上一份报告的 Gap 2（分/合判据）天然可以合并成一篇更完整的工作。

08这个方向的实验平台该怎么搭

最小可行栈

  1. 切分层：CUDA Green Context（首选，有官方 API + PyTorch 2.12 Beta + FlashInfer 支持）；对照组用 MPS ACTIVE_THREAD_PERCENTAGE 与 MIG。libsmctrl 仅在需要 TPC 级掩码且卡是 Ampere/Ada 时用（Hopper 起语义已变）。
  2. 服务层：vLLM 或 SGLang + FlashInfer 后端（因为 FlashInfer 的 green_ctx 是现成的）。
  3. 负载层：ServeGen 生成多租户负载；必须包含算力密度差异极大的租户组合（长 prefill 租户 vs 纯 decode 租户），否则测不出 token 公平的失效。
  4. 测量层：Nsight Systems 看 kernel 在 SM 上的实际落位；DCGM / NVML 采 SM occupancy 与 L2 命中；nvbandwidth 标定带宽基线。

这个方向特有的指标

  • 有效算力达成率 = 实测 FLOPs / 名义分配 SM 对应的理论 FLOPs。这是本方向的核心指标，也是区分「分配」与「保证」的唯一量化方式。
  • 隔离度：邻居负载从空载升到满载时，受保护租户的延迟劣化倍数。MPS 与 Green Context 在这一项上会拉开差距。
  • work-conserving 程度：配额空闲时被其他租户利用的比例。LithOS 的 TPC stealing 就是在优化这一项——保证与利用率的权衡曲线是核心图。
  • 重配置开销：Bullet 强调微秒级，MIG 是「需要 GPU reset」级。做动态分配必须报这个数。
常见坑：用 MPS 的 ACTIVE_THREAD_PERCENTAGE 当硬配额来做 baseline 或结论。它是上限而非保证，且无故障隔离；如果你的实验结论建立在「MPS 给了我 50% 算力」上，审稿人会直接质疑。
