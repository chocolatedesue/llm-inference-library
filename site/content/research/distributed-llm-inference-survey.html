分布式 LLM 推理的并行化
设计空间、前沿论文与实验平台

面向「选题找 gap + 搭实验平台」的调研报告。覆盖 2024 – 2026 年 OSDI / SOSP / NSDI / EuroSys / ASPLOS / MLSys / SIGCOMM / ISCA / FAST 的分布式推理系统工作，并给出 2–8 节点小集群下可执行的实验平台配方。

调研日期 2026-07-26约 90 篇系统论文假设资源：2–8 节点 GPU 小集群

01一句话全景

如果只记一句话：推理的并行化正在从「对整个模型选一种并行方式」，走向「按算子的计算/访存特征、按请求的阶段、按运行时负载，逐块地选择并切换并行方式」。过去两年几乎所有重要工作都是这条主线的分支。

主线一
解耦
阶段解耦（Prefill/Decode）→ 模块解耦（Attention/FFN）→ 角色解耦（Rollout/Train）。粒度越切越细。
主线二
KV 上位
KV cache 从「显存里的中间结果」变成独立于权重的第二调度对象：可分片、可池化、可跨机迁移、可跨模型复用。
主线三
动态化
弹性序列并行、动态 EP 伸缩、在线专家重映射 —— 并行度本身成为运行时可调的变量。
给你的直接结论：纯粹「提出一种新并行切法」的论文窗口已经很窄（TP/PP/CP/EP 的静态组合已被吃透）。2026 年真正有空间的是三类：(a) 并行策略的自动搜索与在线自适应；(b) 并行策略与 KV cache 生命周期的联合设计；(c) Agentic / RL rollout 这类新负载下的并行与调度。第 5 节给出 7 个具体 gap。

02并行轴：设计空间与它们各自的痛点

推理与训练的根本差异决定了并行策略的取舍：训练是吞吐导向的大 batch、无延迟约束、配置一次跑到底；推理则分成 prefill（compute-bound） 与 decode（memory-bound，瓶颈在 KV 带宽），还要满足 TTFT / TPOT 的 SLO。下表按四个关键维度评估六条并行轴。

六条轴的当代组合范式

  • Attention-DP + MoE-EP — DeepSeek-V3/R1 的主流做法。MLA 让 KV 很小，attention 部分直接数据并行复制以规避 TP 通信；FFN 用大规模跨节点 EP 承担主要通信。推理系统说明
  • KV-Parallel（attention 阶段）+ TP/EP（FFN 阶段）动态切换 — NVIDIA Helix Parallelism（arXiv:2507.07120，2025-07）。同一批 GPU 在一次 forward 内切换角色，用 batchwise overlap 掩盖切换通信。这是「按阶段换并行」最激进的一版。
  • Attention/FFN 模块级解耦 — MegaScale-Infer（SIGCOMM'25，字节）与 Adrenaline（AFD）。把 attention（访存密集）与 expert（计算密集）拆成两个独立伸缩的服务单元，ping-pong 流水掩盖 all-to-all。
  • 弹性序列并行 — LoongServe（SOSP'24，北大）按请求实时调整 SP 度，解决长上下文与 decode 混跑的碎片化。

同名不同物：两个 "Helix" 一定要分清

写 related work 时最容易踩的坑之一：

  • Helix（CMU，ASPLOS 2025）— Serving LLMs over Heterogeneous GPUs and Network via Max-Flow。把异构 GPU + 异构网络下的模型切分与请求路由建模成最大流问题。arXiv:2406.01566
  • Helix Parallelism（NVIDIA，2025-07 arXiv）— Rethinking Sharding Strategies for Interactive Multi-Million-Token LLM Decoding。KV 分片 + 阶段切换并行，与前者完全无关。arXiv:2507.07120（vLLM 已有 RFC #34018 在跟进）

类似的还有 DCP（Dynamic Context Parallelism, SOSP'25）与各种 "Context Parallelism"，注意区分训练侧与推理侧。

03范式演进：一条时间线

2022 – 2023
吞吐时代：连续批处理 + 分页显存
Orca 的 iteration-level batching、vLLM 的 PagedAttention 把「怎么把 GPU 喂饱」解决掉。并行仍是训练搬过来的静态 TP/PP。Petals 开辟去中心化推理，AlpaServe 开始做多模型放置搜索。
2024
阶段解耦元年：Goodput 取代 Throughput
DistServe（OSDI'24）与 Splitwise（ISCA'24）确立 prefill/decode 分离；DistServe 同时把评价指标从吞吐改成 goodput（SLO 达标前提下的吞吐），这一框架现在是审稿人的标准检验点。Sarathi-Serve 的 chunked prefill 成为所有生产框架的默认调度原型。Vidur（MLSys'24）让并行配置搜索可以在 CPU 上做。
2025
工业级落地 + KV 成为一等公民
Mooncake（FAST'25，Kimi 生产系统）把 KV cache 池提升为架构核心并开源；DeepSeek 公开 96×H100 的大规模 EP 部署与 DeepEP / EPLB；MegaScale-Infer（SIGCOMM'25）把解耦下推到 Attention/FFN 模块级；WaferLLM（OSDI'25）把并行搬到晶圆级网格；Aegaeon（SOSP'25，北大+阿里云）做 token 级 GPU 池化。同时 PrefillOnly（SOSP'25）指出 RAG/Agent 场景大量请求根本不需要 decode。
2026
重心转向 Agentic / RL 基础设施，以及解耦的「再统一」
OSDI'26 里 RL post-training 基础设施独占 6 篇（RollArt / Weave / RLinf / DynaRL / Seer / RobustRL），核心矛盾变成 rollout 与 training 两类异构负载如何解耦、协同与容错——即 P/D 解耦思想的迁移。同时出现反思：Revisiting Pipeline Parallelism for LLM Serving（OSDI'26）重审 PP 在推理侧的适用性；多篇工作质疑纯 P/D 分离在负载抖动下的僵化，转向可切分的混合架构。

05七个可攻的研究 Gap

按「和你 2–8 节点资源的匹配度」排序：越靠前，越是小集群能做出可信结果的题目。每条都给了 gap 是什么、为什么还没被解决、以及在你的资源下怎么做实验。

Gap 1 · 推理侧缺一个 Alpa —— 联合搜索 TP/PP/CP/EP/解耦粒度的自动并行框架
训练侧有 Alpa 的成熟自动并行搜索，推理侧到今天仍然是「Vidur 模拟器 + 人工经验规则」。Helix Parallelism 这类「一次 forward 内按阶段换并行」的设计出现后，搜索空间进一步爆炸：并行度 × 阶段划分 × 解耦粒度 × 请求路由，且目标函数是 goodput（含 SLO 约束）而非吞吐，是个带约束的组合优化，不是简单的 cost model 最小化。
小集群怎么做：这是最适合 2–8 节点的题目。用 Vidur（误差 <9%）在 CPU 上跑搜索，把真实集群仅用于验证搜索出的 Top-K 配置——这正是 Vidur 自己的方法论（1 CPU-hour 替代 42K GPU-hours）。可信度的关键是：报告「模拟器预测 vs 实测」的误差曲线。
Gap 2 · 解耦架构的「再统一」：什么时候该分、分多细
2025–2026 已有多篇（DynaServe 的 micro-request、Prefill-Decode Aggregation or Disaggregation、Prefill-Decode Multiplexing）指出纯 P/D 分离在流量抖动、小请求、异构硬件下反而变差，但目前没有统一的判据说明在给定负载分布与硬件拓扑下应该选哪种形态。这是一个「理论 + 系统」都还空着的位置。
小集群怎么做：2 节点即可复现分离/合并两种形态（vLLM KVConnector 或 Mooncake Transfer Engine）。用 ServeGen 生成不同 burstiness / 长度分布的负载做 sweep，画出「负载特征 → 最优形态」的相图（phase diagram）。相图本身就是贡献。
Gap 3 · MoE 负载均衡的指标之争尚未收敛
主流 EPLB 类方法均衡的是每卡 token 数；METRO（2025，NVIDIA）指出在 memory-bound 的 decode 阶段应该均衡每卡激活专家数，DeepSeek-V3/Qwen3 上能降 11–22% decode 延迟。而 MLSys'26 的 On the Diminishing Returns of Expert Load Balancing in MoE LLM Serving 又反过来质疑负载均衡本身的边际收益。三种立场并存，说明「什么才是 EP 的正确均衡目标」还没有定论。
小集群怎么做：8 卡单节点即可跑 DeepSeek-V2-Lite / Qwen3-MoE 级别模型的 EP 实验；用 SGLang 或 ktransformers 做基线，profile 出「token 数 / 激活专家数 / all-to-all 时间」三者的实测关系。这题不需要 671B。
Gap 4 · 长上下文下 KV 分片与「投机解码 / 前缀共享」的不兼容
CP / KV-parallel 把 KV cache 跨 GPU 分片之后，投机解码的树形验证与跨请求前缀共享（RadixAttention 类）都会失效或代价陡增——两者都假设 KV 在单一位置可随机访问。这个交叉点在文献里几乎是空白，而它恰恰是「长 CoT 推理 + 多分支采样」这个最热负载的核心矛盾。
小集群怎么做：SGLang（RadixAttention 原生）+ 2 节点 CP，量化「分片度 ↑ → 前缀命中收益 ↓」的曲线，是很干净的 measurement study，也是好论文的第一节。
Gap 5 · Agentic / RL rollout 负载下的并行策略几乎没人系统研究
这是 2026 年增长最快的方向（OSDI'26 六篇 RL infra + NSDI'26 的 Autellix/Agentix）。但现有工作大多在调度层（rollout/train 解耦、tail batching、长尾预测），并行策略层几乎无人涉足：rollout 阶段的最优并行配置与 serving 阶段是否相同？训练与 rollout 共置时权重要不要重切？RL 的同步屏障如何影响并行度选择？公开 agentic trace 也刚刚才有（TraceLab, 2026）。
小集群怎么做：这是「新负载 + 老方法」的典型机会窗口。用 verl / RLinf 类框架在 2–4 节点跑小模型 GRPO，测 rollout 阶段的并行敏感度即可出结论。风险：方向拥挤，出手要快。
Gap 6 · 解耦/并行架构的容错与弹性被严重低估
DéjàVu（ICML'24）之后，P/D 分离下的故障恢复基本无人跟进；OSDI'26 的 RobustRL 做了 RL 侧的角色感知容错，但推理服务侧仍然是空的。当 KV cache 池、prefill 集群、decode 集群、专家副本各自独立伸缩后，「一个 decode 节点挂了，正在生成的请求怎么办」没有标准答案。2026 年的 KV 管理综述也把容错列为七个评测空白之一。
小集群怎么做：容错实验恰恰不需要大集群——4 节点注入故障即可。而且这类工作对 baseline 的性能对比要求低（因为大家都没做），审稿风险相对小。
Gap 7 · 评测方法本身：现有 benchmark 系统性低估了难度
ServeGen（NSDI'26，阿里 35.4 亿请求）用生产数据证明：ShareGPT + 人工 Poisson 的经典做法会让容量规划低估 50%；输入输出长度相关性极弱（推翻先前假设）；到达过程无法用单一分布拟合。这意味着过去两年大量论文的实验结论可能在真实负载下不成立。系统性地重测经典系统，本身就是一篇有价值的 measurement paper。
小集群怎么做：纯软件工作，2 节点足够。拿 DistServe / vLLM / SGLang 在 ServeGen + Mooncake + BurstGPT 三套真实 trace 下重测，与原论文的合成负载结论对比。这是最低风险、最高确定性的一篇。

06实验平台：怎么搭

实验平台分三层：软件基线（在谁身上改）、模拟器（把小集群外推到大规模）、负载与指标（结论是否可信）。对 2–8 节点资源，正确的策略不是「买更多卡」，而是 小集群实测 + 校准过的模拟器外推 —— 这正是 SimAI 论文自身的验证方式。

6.3 负载与 Trace：结论可信度的命门

该用的

  • ServeGen（NSDI'26，阿里，arXiv:2505.09999）— 2025 年 1–4 月、35.4 亿请求、12 个模型、约万级 GPU 的生产数据。2026 年做 LLM serving 实验的首选负载生成器。
  • Mooncake trace（2025-02）— Kimi 真实生产 trace，含时间戳与 cache 命中率（最高 50%），研究 KV 复用必备。
  • Azure LLM Inference Trace 2023/2024 — 最广泛使用的基线 trace，DistServe/Sarathi/Vidur 标配，必须包含以便和已有工作对齐。
  • BurstGPT — 529 万真实 ChatGPT 请求、4+ 个月，突出流量突发性。
  • TraceLab（arXiv:2606.30560, 2026）— 少见的公开 coding agent 工作负载 trace。做 agentic 方向必看。（2026 新作，建议复核）

该停用的

ShareGPT / LMSYS-Chat-1M + 人工叠加 Poisson 到达（即 vLLM benchmark_serving.py 的默认做法）——ServeGen 已用生产数据证明这套组合生成的负载显著比真实流量更「好服务」，会导致容量规划低估 50%。

具体反直觉发现：① 到达过程无法用单一 Gamma/Weibull/Exponential 拟合；② 输入长度是 Pareto+对数正态混合、输出是指数分布，且输入输出长度相关性很弱；③ 2412 个客户中 29 个贡献 90% 流量；④ reasoning 负载呈 bimodal 的思考/答案长度分布。

建议：仍然报告 ShareGPT 结果以便与旧论文对齐，但把 ServeGen / 真实 trace 作为主结果。

6.4 硬件与获取

互联层级（决定你能做哪类实验）

NVLink（节点内）> PCIe > RDMA/InfiniBand（节点间低延迟）> RoCE/以太网。做 P/D 分离与跨节点 KV 迁移，节点间必须有 RDMA/IB 或至少 RoCE，纯 TCP 的结果没有说服力（Mooncake 实测 8×400Gbps RoCE 才到 190 GB/s）。租云时务必确认 SKU 含 InfiniBand。

学术界低成本渠道

  • Chameleon Cloud（NSF）— 2025-06 起 TACC KVM 站点已上 H100
  • CloudLab（NSF）— 网络拓扑可控，GPU 节点较少，但做网络相关实验独一档

07方法论：审稿人会怎么打你

七个高频批评点

  1. 只用 closed-loop 吞吐（固定并发）掩盖 SLO 违反 —— 必须补 open-loop 到达过程。
  2. Coordinated omission —— 测量客户端自身阻塞导致延迟分布失真，尾延迟被系统性低估。
  3. 基线没调到最优 —— baseline 的 batch size / 并行度没扫参就对比，是最常见的 reject 理由。
  4. 只报单一工作点 —— 必须给完整的 request-rate sweep 曲线（吞吐-延迟 / goodput-SLO Pareto）。
  5. 不报方差 —— 多次运行的 variance 缺失。
  6. 用静态数据集 + 人工 Poisson 冒充真实负载 —— 见 6.3。
  7. 回避 goodput 框架，只讲 tokens/s。

该报的指标

  • TTFT（prefill 延迟）、TPOT / ITL（decode 每 token）、E2E，都要 P50/P95/P99。
  • Goodput — DistServe（OSDI'24）定义：满足 SLO（如 90% 请求达标）前提下每 GPU 的最大请求速率。这是当代 serving 论文的默认主指标。
  • Fairness — VTC（OSDI'24）的 virtual token counter，多租户场景必备，有 artifact。
  • Cost-per-token / 能耗 — 异构与成本方向的必需项（可参考 vidur-energy fork）。

工具

vllm bench serve / vllm bench sweep serve 做 rate sweep；NVIDIA GenAI-Perf 已演进为独立项目 AIPerf（2026 仍活跃迭代）。优先用标准化生成器而非自制脚本。

Artifact Evaluation：OSDI / ATC / EuroSys / SOSP 由统一的 sysartifacts 联盟组织，分 Available / Functional / Reproduced 徽章。EuroSys 2025 发布的五年 AE 经验总结指出，失败的主因是 GPU 特定硬件依赖 与 CUDA-driver-NCCL 版本漂移。实践：从第一天就用 Docker/Apptainer 固定 CUDA / 驱动 / NCCL / vLLM commit hash，公开 lockfile。

08如果是我，接下来四周这么做

  1. 第 1 周 · 建地基。在小集群上拉起 vLLM V1 + SGLang 双基线，跑通 vllm bench sweep serve；同时把 ServeGen、Azure trace、Mooncake trace 三套负载接进来。用 nccl-tests + nvbandwidth 把集群的真实拓扑带宽测出来存档——后面所有模拟器标定都要用它。
  2. 第 2 周 · 装杠杆。部署 Vidur，用第 1 周的实测数据标定它，报出「模拟 vs 实测」误差。这一步做完，你就有了「用 8 卡讲 1024 卡故事」的合法性。
  3. 第 3 周 · 打一枪确定性最高的。做 Gap 7（重测经典系统在真实 trace 下的表现）——纯软件、低风险、必出结论，而且这份 measurement 会自然暴露出 Gap 2 的相图边界在哪。
  4. 第 4 周 · 选主攻方向。结合第 3 周的观测，在 Gap 1（自动并行搜索） 与 Gap 2（分/合判据） 之间二选一作为主线——这两个和你的资源最匹配，且都能用「小集群实测 + 模拟器外推」的方法论撑住规模。Gap 5（Agentic/RL）回报高但赛道已经很挤，除非你有独特的 workload 来源。
