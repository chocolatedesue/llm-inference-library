00成熟度标注怎么读

最重要的区分
生产级 vs 论文 artifact
生产级 / 活跃研究项目可以当长期基线，社区会帮你修 bug、跟新硬件。论文 artifact 多数是发论文时的一次性快照，通常锁死在某个 CUDA/框架版本，只适合作为对照组复现，不要在上面长期开发。
四档定义
生产级 活跃研究
论文 artifact 停更/慎用
生产级=有版本发布节奏、被工业界部署；活跃研究=持续更新但 API 会变；artifact=AE 快照；停更=超一年无更新或已被取代。
已核实的星标
仅少数几个
沙箱无法批量访问 GitHub API，所以没有编造星标数。少数抽查过的会在备注里注明（如 kvcached 1.1k、BulletServe 53、Tally 12）。成熟度分档基于调研中确认的版本发布节奏与工业采用情况。

01服务框架：你在谁身上改

这一层决定你的工作量下限。做并行策略/调度选 vLLM 或 SGLang；做细粒度 SM 分配要看 FlashInfer（green_ctx 在这里）；做集群编排才用 Dynamo / llm-d。

03细粒度 GPU 共享 —— 你上一个问题的方向

这一层的代码普遍规模小、星标少，但这恰恰说明方向没被做透。Bullet 是最值得先读的：它把 MPS + libsmctrl 组合起来做 SM 动态分配，代码不长，是这个方向最完整的开源样板。

04模拟器与建模工具

先看清楚边界：这一层的工具只覆盖「集群/请求级」，不覆盖「单 GPU 内 SM 争用」。Vidur 把 GPU 当黑盒（profile + 回归预测算子耗时），明确不建模并发 kernel 干扰；2026 年最新的集群仿真工作（如 Revati 的 time-warp 仿真）也主动声明不建模 GPU 内部争用。所以：做并行策略搜索，模拟器是杠杆；做细粒度算力调度，模拟器帮不上忙。
仓库成熟度是什么你该拿它做什么

casys-kaist/LLMServingSim活跃研究迭代级 HW/SW 协同仿真，可插拔加速器后端；2.0 扩展到异构与分离式，误差 <14.7%异构硬件 / 分离式架构的交叉验证。做自定义加速器研究时优于 Vidur

07如果现在就要动手：最小起步栈

按你两个方向分别给一套。都只需要你手上已有的资源。

方向 A · 并行策略 / 分布式调度

1
vLLM + nccl-tests + AzurePublicDataset
拉起基线，测出集群真实拓扑带宽存档，跑通标准 trace。第一周。
2
加入 ServeGen
换掉 ShareGPT+Poisson，主结果用真实负载分布。这一步决定你的结论是否站得住。
3
Vidur 标定 + 外推
用第 1 步的实测数据标定，报出「模拟 vs 实测」误差曲线，获得讲大规模故事的合法性。
4
Mooncake 或 vLLM KVConnector
做 P/D 分离实验，对照组用 DistServe。

方向 B · 细粒度算力调度

1
精读 BulletServe + kvcached
前者是 SM 动态分配的完整样板（MPS + libsmctrl），后者是这个方向唯一的生产级实现。一天能读完，能省你两周。
2
FlashInfer green_ctx + 单卡
Green Context 划分 SM 跑 prefill/decode 共置，先复现出公开报告的 +34% 量级。单卡就够。
3
NVBit + Nsight Systems
测「名义 SM 份额 vs 实测有效算力达成率」——这是本方向的核心指标，也是区分「分配」与「保证」的唯一量化方式。
4
Orion / Tally 当对照组，VTC 当反例
Orion 和 Tally 是干扰隔离的标准 baseline；VTC 用来证明 token 公平在算力密度不均的租户组合下会失效。
核验说明：BulletServe（53 stars，确认使用 MPS + libsmctrl）、kvcached（1.1k stars，2026-04 有 v0.1.5 发布）、Tally（12 stars，296 commits，含 tally-bench 复现仓库）为本次直接抽查确认。其余仓库地址来自论文原文与官方文档引用，成熟度分档为定性判断（依据调研中确认的版本发布节奏与工业采用情况），不是精确的活跃度统计——沙箱环境无法批量访问 GitHub API，因此没有编造任何星标或提交数字。libsmctrl 的仓库地址请从 RTAS'23 论文中获取（UNC 自托管，非 GitHub 主站）。
